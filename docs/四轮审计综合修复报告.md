## 1. 执行摘要

四轮审计找到了真实且应阻断发布的缺陷，但不能把四份清单直接相加，也不能逐条照抄修法。主要原因是：重复报告同一根因；部分结论遗漏了调用链、路由挂载或读写双方语义；有些建议互相冲突；少数“审查通过”结论覆盖范围过大。

**当前应优先处理的五条主线：**

1. **远程可触发的 hbbs 进程退出**：KeyExchange 长度转换 `unwrap()` 和解密失败 `panic!`，与 release `panic = 'abort'` 组合，属于直接的服务可用性风险。
2. **身份认证与控制权限边界**：普通登录用户可进入服务器命令接口；MUST_LOGIN 在 JWT 密钥缺失时只要求非空 token；LDAP 过滤器未转义；OAuth 身份绑定与最终发 token 缺少必要约束。
3. **数据所有权和事务完整性**：地址簿全量同步跨集合删改、标签同步跨集合影响、集合更新允许修改 `user_id`、事务错误被忽略，可能造成跨用户/跨集合污染和不可恢复的数据丢失。
4. **不可信输入和敏感输出**：未认证遥测写入、代理头可伪造、OAuth 状态和密钥字段过量返回、Markdown 未净化、令牌副本登出不清理。
5. **构建与部署不可验证**：缺失 `api/go.sum` 已实际阻断只读依赖构建；控制通道与三容器网络隔离不一致；首次公钥加载存在竞态；测试与可复现构建门禁不足。

**必须撤回或改写的典型结论：**

- “文件缓存 100% 失效”不成立：写入时把过期时间写入 mtime，立即读取隔离测试通过。
- “封禁用户被全部放行”不成立：全局 Limiter 已提前拦截；真正的问题是代理信任、验证码失败可重复尝试及两类登录流程不一致。
- “`-k _` 不强制 key”不成立：`_` 会被替换成公钥，随后执行 licence key 比较；但它不等于用户身份认证。
- “匿名可直接调用上传/OSS 回调”不符合当前路由：`FileBind(adg)` 被注释。库和控制器隐患仍在，重新挂载前必须解决或删除。
- “JWT 密钥在每次生产登录时由 Rust 打印”证据不足：Rust `generate_token` 当前只查到测试调用；另有实际握手路径的**对称密钥 debug 日志**，应一起删除。
- “Token 续期差 1000 倍”不成立：`Milliseconds()/3000` 数值等于秒数的约三分之一；真正的问题是零值默认、DB 过期与 JWT `exp` 的双重语义。
- “镜像使用仓库内不明预编译二进制”不成立：当前 CI 先从源码构建，再传递构建产物到镜像阶段。

本报告把问题归并为 **20 个修复工作包（F01—F20）**。工作包数量不是独立漏洞数量；每包可包含若干相互依赖的缺陷。优先级按实际暴露面、前提条件与影响确定，而非沿用原报告标签。

## 4. 综合修复工作包

### F01｜KeyExchange 远程进程崩溃与握手秘密日志 — P0，确认成立

**来源**：一轮 #1/#19；二轮 S1/S3/S4；三轮 R1/R2。

**证据**：
- `src/rendezvous_server.rs:623-624`：两个输入数组直接转换为 `[u8; 32]`、`[u8; 48]` 并 `unwrap()`。
- `src/rendezvous_server.rs:1619` 附近：`box_::open` 失败进入 `panic!`。
- `Cargo.toml:74`：`panic = 'abort'`。
- `src/rendezvous_server.rs:630`：debug 日志输出协商后的对称密钥；这是本次补充定位的活跃路径秘密输出。
- `src/jwt.rs:16`：打印签名 secret，当前只确认测试调用可达。

**统一修法**：所有网络输入解析/解密失败返回 `Result`，仅关闭当前连接；在转换前验证数量与长度；删除两类密钥日志。不要通过改成 `panic=unwind` 或 catch panic 代替输入验证。若历史生产日志实际包含密钥，按泄漏处置轮换相应秘密并限制日志访问，不在报告中臆断已经泄漏。

**验收**：缺字段、1/2/3 个 key、边界长度、随机密文和错误密钥全部不能结束服务进程；正常握手和并发连接无回归；日志扫描无 secret、私钥和对称密钥；增加结构化 fuzz target。

### F02｜JWT 准入、令牌生命周期与身份状态 — P0/P1，确认成立

**来源**：一轮 #5/#17/#19；二轮 S2/S6；三轮 R3/G4；四轮 G2/G16 及 JWT 低优先级项。

**证据与影响**：
- `src/rendezvous_server.rs:885-920`：MUST_LOGIN 开启、token 非空、SECRET 为空时不验签。
- `src/rendezvous_server.rs:1276` 附近支持运行时开启 MUST_LOGIN，因此只加启动检查不够。
- `api/service/user.go:89-94`：缺 key 时退化到 `Md5(username + time.Now().String())`；不具备安全随机令牌保证。
- `api/lib/jwt/jwt.go`：只含 user_id/exp，无随机 jti；同用户相同到期秒可能生成相同 token，影响独立会话和吊销语义；Go 解析没有显式限制 HS256。
- `api/service/user.go:499-507` 只延长 DB `expired_at`，不能延长已签发 JWT 的 `exp`。
- `api/http/controller/api/ouath.go:63-117`：把空实体当作 nil 判断，且发 token 前没有统一 `CheckUserEnable`。

**影响限定**：RustAuth 后续仍查 DB 并检查用户状态，所以“禁用用户拿到 OAuth token”不等于所有 Go 受保护 API 随即放行。但如果 hbbs 只验签和 exp，而不检查实时用户/会话状态，仍可能出现跨服务边界差异，不能因此忽略。

**统一修法**：
1. API 使用必填的高熵 JWT 密钥；与 hbbs 通过同一 secret 来源配置，明确最小强度，缺失拒绝启动，不自动生成各自不同的 key。
2. MUST_LOGIN 的启动、运行时启用、每次请求三处都 fail closed；错误配置不能使鉴权降级。
3. 签发前统一验证 `u != nil && u.Id != 0` 及账号启用状态；Login 返回 error，签名/持久化失败不返回成功。
4. 显式限定 HS256，加入随机 jti、iat，校验必需 claims；严格解析 Bearer 前缀，拒绝空令牌和格式错误。
5. 推荐当前协议下先确立**固定有效期、到期重新登录**这一完整策略，删除仅延长 DB 的伪续期逻辑；若产品明确需要刷新，则必须端到端返回新 JWT 并实现单次刷新/吊销，不增加“DB 延长但 token 不换”的半套机制。
6. 文档明确 hbbs 离线验签的吊销延迟。若要求注销/禁用立刻影响信令，需明确采用在线会话校验或可靠吊销机制，并对校验不可用 fail closed，不能声称查 Go DB 已覆盖 Rust。

**验收**：空 key/错 key/错算法/缺 exp/过期 token/任意非空字符串被拒；两个同时登录获得不同 jti；禁用、删除账号不能签发有效会话；运行时开启 MUST_LOGIN 不绕过配置检查；DB 与 JWT 到期行为一致。

### F03｜服务器控制接口越权、命令破坏与安全控制通道 — P0/P1，确认成立

**来源**：一轮 #2/#6；四轮 G17/G18。

**证据**：
- `api/http/router/admin.go:59-65`：`/rustdesk` 四个命令路由只继承 BackendUserAuth，没有 AdminPrivilege。
- `api/service/serverCmd.go` 仅连接 loopback TCP；三容器默认网络中 API 的 loopback 不是 hbbs。
- `src/rendezvous_server.rs:1244-1251`：always-use-relay 分支错误发送 `Data::RelayServers0(rs.to_owned())`，可能把 Y/N 当作中继列表。
- `src/rendezvous_server.rs:1292`、`src/relay_server.rs:367`：控制命令依赖 loopback 边界。

**统一修法**：
- 四个控制路由统一 AdminPrivilege，后端做有限命令枚举、参数验证、审计，不只靠前端隐藏。
- 修复 always-use-relay 更新目标，并测试该命令不改变 relay servers。
- 控制通道保留时，推荐明确隔离的本地 IPC，例如仅 API 与服务端共享的 Unix socket 目录，限制目录/套接字权限、检查对端身份；这比把无鉴权控制 TCP 绑定到容器网卡更稳妥。
- 不把“配置目标主机 + 监听 0.0.0.0”当作完整修复，不伪造 loopback 头绕过授权。若确需跨主机控制，采用成熟的双向认证通道和细粒度授权。
- SendCmd 增加连接、读写 deadline 与明确响应 framing，去掉 sleep100ms + 单次读1024字节的隐含协议假设。

**影响限定**：默认三容器布局可能让越权命令暂时发送失败，但不消除授权缺陷；部署打通后会立即扩大风险。

**验收**：普通用户访问四接口均 403；匿名拒绝；未授权容器/本机用户不能控制服务；开启强制登录受密钥配置约束；非法命令不改变状态；三容器控制与中继配置端到端可用。

### F04｜LDAP 过滤器、DN 和本地降级认证 — P0/P1，确认成立

**来源**：一轮 #4；四轮 B4/G15；本次补充认证降级路径。

**证据**：
- `api/service/ldap.go:320-330,399-401`：username/email 原样插入过滤器。
- `api/service/ldap.go:175-183,474-481`：用于 BaseDN 的完整 DN 被 `ldap.EscapeFilter` 处理，混淆 DN 与过滤器编码。
- `api/service/ldap.go:507-539`：EnableAttr 或值缺失即 Enabled=true，AD 默认属性与状态判断的默认行为不一致。
- `api/service/user.go:48-59`：LDAP 禁用、拒绝、网络错误等所有失败都转向本地密码校验。

### F05｜OAuth/OIDC state、绑定唯一性与邮箱合并 — P0/P1，确认成立，利用条件需区分

**核心证据**：

- `api/model/oauth.go` 与 OAuth 回调：`AutoRegister *bool` 可 nil，但存在直接解引用；更新又绕开 FormatOauthInfo。

**必须避免的误修**：浏览器确认登录本来就可能由另一设备上的登录用户完成，不能把“确认用户不同于匿名发起设备”一律判为攻击；真正要绑定的是 flow/action、发起会话/绑定主体、provider 与结果领取凭据。回调后客户端仍需轮询，不能在 callback 一刀切删除整个 state。

**统一修法**：
1. 采用明确的状态转换：创建 → provider 已验证/等待确认 → 已授权 → 已领取/失效；不同 action 有独立允许的转换。
2. 绑定流程固定发起账号；确认不能任意替换已绑定主体；授权码/领取凭据具备足够熵且只向应有参与者暴露；UI 显示待授权设备和提供方。
3. 最终消费原子且单次；返回缓存快照而不是共享可变指针。单实例可用现有互斥锁实现，不为当前需求预建分布式系统。
4. 第三方身份以稳定 provider 身份 + subject/open_id 唯一；数据库约束和事务兜底并发，不能只靠进程锁或先查后写。Provider 标识不应随意修改而割裂既有绑定。
5. 推荐删除隐式邮箱自动合并：已有本地账号必须登录后显式绑定。即便 provider 声称 email_verified=true，也不应把不同 issuer 的相同邮箱无条件等同为同一主体。
6. AutoRegister 在入口形成明确的非空布尔语义；新增/更新共用领域校验；配置错误直接拒绝，不静默默认开放注册。
7. 全链路检查事务错误；已绑定身份不能再绑定到另一用户；失败不能留下半个新账号/第三方记录。

**验收**：未知/过期 state、错误 action/provider、非发起用户绑定、重复 callback、并发 poll/confirm、账号已删除/禁用、未验证邮箱和重复第三方身份均有负向测试；合法跨设备确认仍可完成；`go test -race` 覆盖缓存状态转换。

### F06｜代理信任、验证码和登录防爆破 — P1，部分成立

**来源**：一轮 #3；二轮 S5；三轮 G7/G8。

**证据**：`api/http/http.go` 未配置 TrustProxy 时保留 Gin 默认全信任；`src/rendezvous_server.rs:1352`、`src/relay_server.rs:405` 直接采用 WS 头中的真实 IP；验证码失败不消费；API 与后台登录成功清理行为不同。

**统一修法**：
- Go 默认不信任代理，显式 `SetTrustedProxies(nil)`；实际反代 CIDR 由部署指定。不是无条件“只信 loopback”，容器反代通常不是 loopback。
- Rust 根据 TCP 原始对端是否可信决定是否接受转发头；拒绝直接互联网来源伪造；正确解析 IPv4/IPv6 和代理链，禁止把任意头当作最终身份。
- 验证码每次尝试即消费，或使用严格的失败次数上限；统一账号/IP 维度速率限制，成功按设计清理失败记录。
- 客户端不支持验证码时采用明确的限速/封禁响应，不把网页登录交互强行套到客户端协议。

**验收**：伪造 XFF/X-Real-IP 不能绕过封禁或污染审计；真实可信反代仍记录用户 IP；错误验证码反复猜测有上限；并发登录不能绕过计数；成功不能清除其他账号的风险记录。

### F07｜遥测、审计写入和设备身份 — P1，确认存在未认证写入，影响需限定

### F16｜WebSocket 加密路径与转发性能 — P1/P2，结构问题成立，客户端影响待验证

**来源**：一轮 #21；二轮 O4；三轮 G8。

`src/rendezvous_server.rs:1339-1404`：TCP 分支握手并解密，WS 分支直接送入 handle_tcp；发送侧 Wss 可以安装 encrypt。正常 WS 初始 encrypt=None，不能仅凭分支不同断言所有 WebClient 已坏；但收到 KeyExchange 后可能进入收发不对称状态。

**统一修法**：先根据当前支持客户端验证实际协议，再选择唯一明确的 WS 策略：完整的应用层握手/加解密，或明确仅 TLS 且拒绝不支持的应用层 KeyExchange。不要随意给已工作的 WS 协议添加另一套加密。限制帧大小、超时和异常关闭；转发复制优化在 profiling 后进行，优先现有 Bytes/库能力，不自行重写传输栈。

**验收**：TCP、WS、WSS 实际客户端正向联调；WS 注入 KeyExchange/畸形帧不会进入半加密状态；转发优化前后吞吐、CPU、内存和消息一致性可比较。

## 5. 统一架构决策：哪些原修复建议不采纳

| 不采纳的直接修法 | 原因 | 统一决策 |
|---|---|---|
| API 缺 JWT key 时自动生成，或换另一种 token fallback | 跨进程密钥不一致；把配置错误藏成运行差异 | 显式共享 secret，缺失失败 |
| 仅在 hbbs 启动时检查 MUST_LOGIN | 运行时控制命令可再次开启 | 启动、启用、请求三层一致失败关闭 |
| 把所有路由都放 RustAuth 后 | 登录、OAuth callback、公开能力会被自锁 | 公开/引导/用户/设备分组，逐路由建立测试 |
| 开放控制 TCP 到 0.0.0.0 解决三容器不通 | 破坏原 loopback 信任边界 | 隔离 IPC 或成熟双向认证通道 |
| OAuth 回调后立刻删除所有 state | 客户端仍需轮询领取结果 | 阶段化状态机，最终原子单次消费 |
| 仅凭 email_verified 自动合并所有同邮箱用户 | 不同 issuer 和账号来源并不天然等价 | 已有账号显式登录后绑定 |
| DB 层先查是否重复，再插入 | 多进程/并发下仍竞态 | 明确唯一约束 + 原子事务/冲突处理 |
| 对所有字段改成 map Updates 就算修好 | 零值更新正确不代表领域不变量完整 | DTO 白名单 + 领域服务约束 |
| 删除用户时把所有日志一并级联删除 | 破坏审计留存与追责 | 会话/业务关系清理，审计单独保留/脱敏策略 |
| 一律加 WAL/timeout、缓存框架或新配置层 | 未确认默认和瓶颈，增加复杂度 | 检查现有库、实际 PRAGMA 和负载，最小实现 |
| 为暂不支持的旧配置写兼容和 migration | 违反项目约束 | 直接统一契约；旧数据冲突显式报告，不静默修复/猜测 |
| 先大量清理再恢复构建 | 失去可验证基线，风险不可归因 | 先最小端到端跑通，再按模块独立修复 |

新增唯一约束之前必须检查已有冲突数据；若存在重复，发布应明确失败并提供冲突清单供授权处置，不自动选一条、静默丢数据，也不随手重建整个库。**备份和部署前检查不是兼容层，不因“不写 migration”而省略数据保护。**

## 7. 验收矩阵与关闭条件

| 领域 | 必需测试 | 判定失败的典型情形 |
|---|---|---|
| Rust 握手 | malformed keys、坏密文、并发、fuzz、日志脱敏 | 单连接输入导致进程结束；日志含协商密钥 |
| 命令控制 | 匿名/普通/管理员权限，非法命令，IPC 对端，relay 状态 | 普通用户可关闭登录；Y/N 改坏 relay 列表 |
| JWT/会话 | 缺 key、错算法、exp、jti、双登录、注销、禁用 | 任意字符串通过；同秒双登录共享 token；DB 延长但 JWT 失效 |
| LDAP | 特殊字符、复杂 DN、禁用、组、断网、本地同名账号 | 注入改变过滤器；LDAP 拒绝后本地降级 |
| OAuth | action/provider/owner、未验证邮箱、重复 callback、并发 poll、nil 配置 | 一份 state 多次发 token；同一第三方身份绑定两个本地用户 |
| 地址簿 | 两用户多集合、空同步、恶意 owner/row_id、DB 故障 | 非目标集合变化；事务部分提交 |
| 用户/组 | 最后管理员并发、账号删除、组成员、token-log 关联 | 零管理员；删除后残留有效会话；错会话吊销 |
| API 输入 | 类型错误、短 token、分页上限、UUID 数组、DTO | 非法输入 500；返回 verifier/client_secret |
| 代理/限流 | 直接来源伪造头、可信代理、验证码重试、并发 | 可随意改变限流身份；猜测次数无限 |
| 浏览器 | Markdown payload、logout、OAuth 回跳、站外 redirect、主题 | JS 执行；token 副本残留；state 丢失 |
| 运行部署 | 全新目录、非 root、密钥权限、HTTPS、端口、两架构 | 空公钥仍 healthy；API 可读私钥；命令口暴露公网 |
| 构建 | clean checkout、锁文件、readonly、fmt/vet/test、镜像来源 | 构建改锁文件；测试未运行就发布 |

**关闭一项所需证据**：当前代码差异、对应负向测试、运行结果、影响范围说明。仅“写了修复代码”“加了一个 nil 判断”“编译通过”不能关闭权限/事务/协议类问题。

## 9. 本次复核补充发现与最终结论

在四轮原意见之外，本次沿调用链发现或明确化了以下必须一并处理的问题：

1. 握手对称密钥 debug 日志比仅测试调用的 JWT 生成日志更接近生产活跃路径（F01）。
2. MUST_LOGIN 运行时开关使“只做启动校验”的方案不完整（F02/F03）。
3. LDAP 所有认证失败都降级到本地密码，可能削弱目录禁用/允许组边界，取决于本地同名账号凭据是否存在（F04）。
4. OAuth sync.Map 中存可变指针，最终 get/delete 不是原子消费；缺少阶段语义会让简单“删 state”修法破坏正常轮询（F05）。
5. Go 的会话 DB 续期不能续签 JWT，Rust 离线验签与 Go 即时 DB 检查存在生命周期差异（F02）。
6. FileCache 的问题不是 TTL 比较，而是写入发布和读取并发窗口；无业务调用的缓存优先删除而非扩建（F13）。
7. 现有唯一性检查若只靠进程锁或先查后写，不能解决多实例和并发；新增约束必须显式报告现有冲突，不自动丢数据（F05/F07/F09）。

**最终建议**：把本报告作为修复主清单，四份原审计作为证据来源保留。先恢复可重复验证，再修远程崩溃、认证/控制边界、身份绑定与数据所有权，随后完成部署闭环；最后收敛死代码和样式。所有问题以代码、测试和实际部署行为关闭，不以“上游一直如此”“另一轮说没问题”或“默认部署恰好不可达”关闭。

**当前状态：分析与方案完成，业务修复尚未实施；Go 全量验证被依赖校验文件阻断，Rust 运行验证受工具环境限制。**
